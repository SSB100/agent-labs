# POD failed-pass recovery

Status: implementation and focused qualification; no live authority.

## Decision

Resume the same logical research goal with a new complete evidence pass. The
predecessor pass remains incomplete and its reviewer response remains rejected.
There is no formatting model call, rewritten review, retroactive acceptance,
replacement receipt, or reuse of that response as an accepted dependency.

The new planner receives a bounded projection of the four accepted outputs:
prior queries and candidate labels, selected evidence views, assessment summary,
recommendation and limitations, plus the four output hashes. The saved rejected
critique accompanies this projection as explicitly untrusted historical context. It chooses new queries and sources
under the unchanged public-source policy. A new ordinary independent review is
required before a result may be presented as reviewed. Supplier-only findings
should prompt independent evidence gathering; no review text can authorize
Etsy scraping, account access, private-data use or a suggested transaction.

## Minimum persistence boundary

- Existing scope/plan formats and worker packs remain byte-compatible.
- A new recovery-only template version is explicitly reviewed and installed;
  existing templates and approvals never acquire recovery permission.
- One immutable recovery link binds the new setup, policy, scope and successor
  plan to the stopped predecessor, failed observation/diagnostic, four accepted
  dependencies, same Goal, original allowance and exact used exposure/counts.
- Confirmation appends one R07 plan and compares-and-swaps its head using the
  existing owner-episode pattern. It preserves dispatch/child/repair counters.
  Fresh-policy children require new records, so the reviewed physical-child
  ceiling is prior children plus five, without increasing paid calls or passes.
- No historical policy is unrevoked, deadline extended, attempt edited, unknown
  charge erased, new Goal created, funding root replaced or cap increased.
- A fresh explicitly approved recovery window governs only the new policy.

## Failure eligibility and trust

A diagnostic mentioning `max_length` is not enough. Validate the complete saved
response, all original structure and review-domain rules, accepted dependency
proofs and settled cost. Only exact prose maxima may have failed. Even then the
response is unaccepted: eligibility describes a technical failure, not a newly
qualified independent review. Historical prose and proposed actions are never
execution authority. No model paraphrase is claimed semantically equivalent.

## Required focused acceptance

1. Reproduce the six retained prose-length failures; additional structure,
   prototype-key, evidence-reference and verdict defects fail closed.
2. Owner page reports rejected review rather than stale `dispatched`, preserves
   Stop and cost visibility, and does not offer blind Continue.
3. Prepare/confirm uses the same Goal, explicit recovery template and fresh
   approval; duplicate/raced confirmation creates at most one successor.
4. A stopped policy cannot send; old calls, costs, deadlines and observations
   remain byte-identical. New template alone cannot activate any owner.
5. New planner sees labelled failure history, not an accepted review; it cannot
   send private context or select prohibited sources. It forms a new query.
6. Full five-phase recovery yields a genuinely reviewed sourced result or honest
   insufficiency. Cumulative call/pass/receipt/spend limits survive concurrency,
   timeout, redeploy and Stop, including an exhausted whole-pass boundary.

Production migration, capability installation and the new recovery grant/window
require the exact reviewed approval bundle after focused qualification.

## Reviewed database change and release boundary

Migration: `supabase/migrations/20261012131500_r12_pod_failed_pass_recovery.sql`.
It adds one private append-only recovery-link table, a private activation view,
owner-only read/prepare/confirm entry points and narrowly linked successor guards.
Existing ordinary activation continues to require template `.2`; only the new
recovery entry point accepts separately installed template `.3`. Both preserve
current owner checks, Business locking, scoped server keys, R05 admission, R07
leases/CAS, exact dependency/source pins, Stop and receipt handling. API roles
cannot write private recovery rows or call its internal helpers directly.

Installation does not install a template, create an owner grant or spend money.
The prior app remains compatible during the definition installation. Unexpected
errors can block recovery or affected reads; the migration is one transaction
and any failed installation rolls back. Once committed, a code rollback alone
must not pretend that a confirmed recovery plan is an ordinary v1 plan. Leave
old grants stopped, use the supported Stop action if a new grant exists, and
retain the migration/history while diagnosing; any schema rollback needs its
own reviewed procedure.

Capability installation reuses the exact existing worker/workflow manifests,
catalog rows, source policy (including all six exclusions), application-key
hash and source/retention bounds. It appends a `.3` template with the new reviewed
planner-system pin and distinct recovery execution/eligibility/policy review
pins. It must not modify the `.2` template or its grant. The release evidence and
installation bundle are verified once at installation; executing release
provenance is still saved for every paid response. Compatible later code fixes
do not change an owner's unchanged goal/source/budget permission.

  non-length/schema/domain defects, owned prototype names, honest failed status,
  owner consent and retry identity, and ordinary flow compatibility.
- Isolated SQL/controller/adapter transport covers a real rejected response,
  Stop, same-Goal confirmation, a new full reviewed result, exhaustion at the

  unsent-reservation cancellation. These are synthetic technical fixtures.
- The native CI branch uses separate connections and observed Business-row lock
  waits for confirmation/Stop races, plus a fresh anon backend's first successor
  dispatch under the unchanged three-second SQL deadline. Native success is not
  claimed until that exact-head CI result is available; it does not reproduce
  Production hardware or every possible contention pattern.
- The actual retained public prose was inspected offline: original review 3,905
  UTF-8 bytes, bounded history 9,730 bytes, actual-dispatch-shaped request 16,503
  bytes and serialized wire body 14,873 bytes, all inside the existing 24,576
  byte bounds. Future identifier hashes used fixed-width placeholders. This is
  a serializer proof, not a live send or market-evidence qualification.
- SQL and JavaScript both reject non-length defects. The reused SQL schema
  validator counts minima in Unicode code points while JavaScript counts UTF-16
  units, so an emoji-heavy edge case may conservatively fail recovery.
- Query duplicate rejection uses the existing normalized exact-query rule
  across the linked predecessor and new scope. A materially different inquiry
  and independent sources are planner instructions, not claimed semantic proof.
- The lineage allows one recovery from original v1 only. Another rejected
  response cannot recursively create allowances or renew access.

The current saved research is insufficient evidence: all four retained sources
were supplier-authored, and no accepted independent recommendation exists.
Technical fixture outputs cannot be presented as a real researched result.
