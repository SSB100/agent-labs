## Minimal additive persistence

Migration `20261003024549_r04_business_quest_identity.sql` creates nine private tables: `r04_business_versions`, `r04_business_state`, `r04_goal_versions`, `r04_goal_state`, `r04_envelopes`, `r04_confirmations`, `r04_revocations`, `r04_research_links`, and `r04_submissions`. They use UUIDs, UTC timestamps, monotonic revisions, bounded JSON and composite Business references. All enable RLS without direct public/anon/authenticated/service-role table access; guarded owner RPCs provide access. Immutable history rejects update/delete, and foreign keys prevent deleting referenced identities.

| Record | Contract |
| --- | --- |
| Business settings revision | `business_id`, `revision`, immutable brand/context, operating rules, allowed activity descriptions, explicit restrictions, creator/time, canonical content hash. No account secrets, profile fields or implied authorization. Current revision pointer is updated only with compare-and-swap. |
| Business operational preference | Business-bound state `setup`, `paused`, `stopped`, revision/time. A future `operating` transition is reserved for reviewed R05 admission. Existing Businesses without a row project as `legacy_unmanaged`, not paused or authorized. |
| Goal revision | `(goal_id,business_id,revision)`, original screened intent, parsed objective/target, exact money and date fields, ambiguity flags, content hash, creator/time. `goals.id` is the owner-facing Quest ID. A current revision pointer may change atomically; historical revisions never change. |
| Quest lifecycle preference | A Business-bound record keyed by existing Goal ID tracks `draft`, `ready`, `paused`, `stopped`, `completed`. Execution is unavailable and target achievement is unverified; no R04 API records a verified result. Core Goal remains `draft` for new R04 Quests. `active`/`achieved` are not assigned from a save or unchecked owner target claim. Existing Core Goal statuses are preserved. |

| Envelope confirmation | Append-only owner actor/time, exact proposal ID/hash, exact revision references, idempotency key and request hash. Unique experiment association prevents conflicting canonical Quests. The dry-run projection reports failed linkage reasons without storing guessed links. |

Do not store installed pack contents again in Business rules: reference exact existing installation/release IDs and hashes. Likewise account references contain safe ID, provider, revision and display label only. Current registry state is re-read for confirmation; labels never establish identity. No saved-account reuse across Businesses is introduced.

`r04_submissions` stores immutable per-Business submission UUID, canonical request hash, actor and response. It supplies transactional duplicate detection separately from revisions and confirmations.

## Intake and money/date contract

Use a pure deterministic parser with no model, network, provider, quote or workflow dispatch. Support a small documented grammar and explicit corrections; retain unknowns rather than manufacturing precision. Save incomplete drafts, but require resolution of consequential ambiguities before marking ready or confirming an envelope.

Supported structured facts are objective, target metric (`revenue`, `realised_profit`, `units`, `orders`), target amount/currency, budget amount/currency, project deadline/date/time/timezone, geography, scope and stop constraints. Custom metrics remain unsupported. Monetary decimals use strings with up to twelve whole-number digits and six fractional digits. SQL independently rejects missing consequential facts at ready/propose, even if a caller clears the ambiguity list. Target must be positive; zero budget is allowed. Currency is mandatory for revenue/profit and budget, and forbidden for unit/order targets. `$500` alone is ambiguous. Revenue cannot become profit; an aspiration is not evidence of achievement.

Preserve the original date phrase separately from an explicit timestamp and IANA timezone. Ambiguous dates such as `03/04`, absent year/timezone and relative deadlines require clarification or explicit acceptance of a displayed interpretation. Project deadline, envelope authorization expiry, provider lease expiry and Knowledge freshness are independent fields. Never copy one into another silently.

Reject credential-like input before server persistence, error logging or any future model boundary. Apply screening to client draft serialization as well: raw text must not first enter sessionStorage and only later be checked on submit. Reject recognized tokens, private keys, authorization headers, credential URLs and explicit password/secret assignments; use bounded generic error codes without reflecting input. Direct users to secure Connections. A heuristic is defense in depth, not a claim that arbitrary secrets can always be detected. All server writes revalidate and bound inputs independently of browser checks.

## Owner APIs and concurrency

Types are in `src/core/quest-contract.ts`. Implemented RPCs:

- `r04_quest_transition(p_business_id,p_operation,p_payload,p_submission_id)`: `business.save`, `quest.save`, `quest.preference`, `quest.select`, `envelope.propose`, `envelope.confirm`, `envelope.revoke`, `research.link`. Business creation remains the existing separate action; `business.save` initializes/revises settings for an existing owned Business. Quest creation inserts a Core Goal once; later edits append overlay revisions without rewriting that initial Goal row.
- `r04_quest_read(p_business_id,p_goal_id=null,p_limit=20,p_offset=0)`: exact optional Quest, independently counted page (maximum 50), current/last selection, latest ten proposals with completeness flag, and safe account/pack reference lists limited to twenty each with completeness flags. Missing or foreign explicit IDs fail; no fallback.
- `r04_research_link_preview(p_business_id,p_experiment_id)`: bounded read-only association evidence; statuses `linkable`, `legacy_bound`, `unlinked_ambiguous`, `unavailable`. Maximum 100 authority roots/500 experiment records. `legacy_bound` is informational, not an enabled link action.

None starts work. All results report `executionAvailable=false`; proposal `effective` is always false. Confirmation status means the owner recorded exact intent, not permission for runtime dispatch.

Every write requires authenticated `auth.uid()`, direct `businesses.owner_user_id` check, explicit Business ID, expected current revision and stable client submission UUID. Lock the Business first, then Goal/current revision rows in a consistent order. Same submission key plus identical canonical request returns the same record/result; same key plus different request fails. Do not create a fresh UUID on every server retry. Untrusted submitted hashes are recomputed server-side. Transaction failure leaves no partial Goal/revision/confirmation/event.

Confirmation locks the exact current revisions and rechecks account/provider revision/status, pack pins, required facts, expiry and proposal hash in that transaction. A settings/Goal edit concurrently racing confirmation either wins first and makes confirmation stale, or wins afterward and makes it ineffective. Retrying a historic successful confirmation returns its receipt with current `stale` status, never a new grant. Deleted, inaccessible, changed or unknown references cannot be treated as empty or approved.

Use empty `search_path`, schema-qualified names, explicit function execute revocations and allowlisted grants. Review security-definer ownership and any function reachable by `anon`, `authenticated` or `service_role`. Existing broad Core Goal owner policies must not allow direct edits to bypass managed revision/confirmation invariants: fence R04-managed Goal rows at the database layer and test direct DML, while preserving unrelated legacy behavior.

## Selection and lifecycle semantics

An explicit `(business,quest)` URL must resolve exactly and be owner-verified. A malformed, missing, foreign or different-Business Quest is unavailable; never substitute another Quest. Selection has no state transition or authority effect.

Without an explicit Quest, prefer the saved same-Business current selection if available. Otherwise show the latest same-Business Quest by `(created_at DESC,id DESC)` as **last Quest**, including its true state; do not call it running. If the current pointer becomes unavailable, show that fact and offer an explicit choice. Keep the current pointer on the Business (one owner today), with a same-Business FK. Selecting or creating a Quest cannot change Business state.

`draft -> ready` means facts are sufficient to review. `ready -> paused/stopped` stores owner intent about future work. `completed` is an explicit owner conclusion with target achievement still **unverified**. R04 has no met/not-met financial-result transition. R07 will govern running transitions, objective progress and evidence-backed achievement. A completed Quest never automatically stops or authorizes continuing the Business.

**Pause enforcement boundary:** saving a Business/Quest pause preference is not an emergency stop for existing research/provider dispatchers. In R04, label it as a saved preference with execution controls unavailable, or withhold the control. Do not display “all work stopped.” All new R04 execution paths remain unavailable. If an implementer exposes a real Pause Business action now, it must first integrate every affected dispatch boundary, queues/reservations/in-flight settlement semantics and race tests; that is R05 scope. Existing specific operational controls retain their own documented scope.

## Legacy association and migration mapping

1. Never edit old migration files, historical intent JSON, `workflow_runs.input`, pack snapshots, roots/round IDs, receipts, funding approvals or cost ledgers.
2. Existing non-null `workflow_runs.goal_id` is the primary canonical association, subject to exact same-Business validation. Unversioned legacy Goals return `legacy_bound` with their original Goal ID. R04 does not import/freeze/edit them or promise a new version. Managed editing/adoption of these legacy Goals remains unqualified; existing canonical linkage remains visible without a misleading link button.
3. For v2 research, validate every included root: `workflow_runs.input.intentId = product_experiments.id`, matching Business/workflow, exact immutable intent identity, and the existing authority helper's parent-path checks. For a new association, the managed Quest's original intent must exactly match the preserved research objective. Preserve `budgetAuthorityRootId`, `semanticGoalHash`, original intent and all prior approvals unchanged. One validated authority chain can acquire one canonical Goal and immutable mapping; its budget remains the old research budget.
4. Distinct existing Goal IDs in one chain, conflicting associations, malformed IDs, absent roots, cycles or missing evidence are `unlinked_ambiguous`/`unavailable`. Equal wording or semantic hash alone does not establish authority or permit merging.
5. Add association records for old immutable experiments rather than adding/updating `goal_id` on terminal experiments. For new workflow launches once separately integrated, populate existing `workflow_runs.goal_id` at creation and pin the Goal revision outside strict legacy input JSON. R04 itself does not introduce launches. Historical workflow rows may be projected through associations without rewriting them.
6. Plans/evidence/products derive linkage through their exact same-Business workflow/experiment parent. Do not infer by title, latest record or candidate alone (a product candidate can participate in multiple experiments). When a direct independent association is required, use a typed same-Business FK relation, not an unchecked generic ID.
7. Migration can install schema with all legacy rows still visible as unlinked. A bounded dry-run report precedes backfill; reruns are idempotent, conflicts are reported, and original row/hash/receipt counts are compared. Installing schema and applying a live backfill require separate deployment authorization.
